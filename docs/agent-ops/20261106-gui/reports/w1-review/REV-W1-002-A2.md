## 4. Findings

### R-W1-002-A2-01 — MAJOR — `ApplyImGuiStyle` re-apply path for `ScaleAllSizes` accumulates / skips, contradicting the task's "DPI applied once" contract

- **Location:** `src/ui/theme/ThemePalette.cpp:49-51, 114-116` (logic unchanged by the diff; surfaced by T-001).
- **Evidence:** `style.FontScaleMain = scale;` (@:51) is absolute (fine). The companion `if (scale != 1.0f) { style.ScaleAllSizes(scale); }` (@:114-116) uses ImGui's accumulating API `_MainScale *= scale_factor` with lossy `ImTrunc` on every style float (@ `_deps-src/imgui/imgui.cpp:1595-1600`), and the guard skips the call when the incoming scale is `1.0f`. `ApplyImGuiStyle` is re-invoked on live monitor content-scale changes (`src/ui/MainWindow.cpp:242-246`, `src/ui/Overlay.cpp:~248`).
- **Why it matters:** on a live DPI move (e.g. 125%/150% -> 100%), `FontScaleMain` resets correctly but the style floats (padding/rounding/scrollbar/item spacing) remain scaled and `_MainScale` keeps the last factor; repeated moves compound. Fonts are unaffected (ScaleAllSizes does not scale fonts — verified), so this is a *layout* drift bug in the exact function the task owns for DPI correctness, and the implementer's own brief (`W1-IMPL-A2.md:41`) already forbade repeated `ScaleAllSizes`.
- **Recommended fix:** only invoke `ScaleAllSizes` when the applied scale actually changes (track last-applied scale per context), or reset via a freshly initialized style; keep `FontScaleMain` assignment absolute.

### R-W1-002-A2-02 — MAJOR — Changed behaviour (AC1 removal, scoped `PushFont`, single-DPI) has no automated regression coverage

- **Location:** `tests/test_overlay_settings_ui.cpp:221-228` (added) and the diff hunks in `src/ui/*`.
- **Evidence:** reviewer independently confirmed (blind pass + claims audit) that no test references `SetWindowFontScale`, `PushFont`, `FontScaleMain`, `FontSizeBase`, or `FontWindowScale`; AC1 was verified only via post-change `git grep`; the W0 investigation and the implementer both noted the gap; the sibling test reviewer (W1-REV-A2T, `reports/w1-review/REV-W1-002T-A2.md`, R-W1-002T-A2-01) independently raised the same finding as **MAJOR**.
- **Why it matters:** the core deliverable of T-001 (behavioural swap of the obsolete font mechanism) is only source-greppable; a regression reintroducing the obsolete API or double-applying a scoped design px would not fail CI.
- **Recommended fix:** add an ImGui-free regression guard (source scan of `src/ui/` for `SetWindowFontScale` / stale font-scale state, and/or a token/mechanism assertion set), per the sibling's P1.

### R-W1-002-A2-03 — MINOR — Design-px token set does not encode the mockup's mid-scale body step (s4=14) / helper (s5=13); token comment merges the two

- **Location:** `src/ui/theme/ThemePalette.h:99-107` (tokens), `docs/design/mockup.html:137-141` (`.s4 { font-size: 14px; }`, `.s5 { font-size: 13px; }`), `docs/design/mockup.html:104-119` (body-level classes at 14, helpers at 13), implementer report §14.
- **Evidence:** mockup type scale: s1=28, s2=18, s3=15, s4=14, s5=13; token `font_body_px = 13` with comment "body / helper text". Task AC2 stated body ≈13 px, so the token is AC-compliant; the mockup mapping is nonetheless incomplete and the added test is named `"design px font tokens follow the mockup type scale"` while asserting only five constants (incl. body=13).
- **Why it matters:** design-fidelity drift risk; test cannot detect a token-set drift at the 14 px step.
- **Recommended fix:** split body/helper tokens or pin the approved mapping explicitly in the test.
