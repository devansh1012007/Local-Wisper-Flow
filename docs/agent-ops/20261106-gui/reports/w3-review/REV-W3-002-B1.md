## 1. Blind-pass findings (before reading implementer reports)
1. **Scope is correct for the stated defect.** `commit_mutex_` (DictationEngine.h:117) is held via `lock_guard`
   (DictationEngine.cpp:231) across the entire check-slice-advance-commit sequence: reload of `silence_start`
   (232), `total`/`committed` loads (236-237), guard checks (238), thresholds (247-250), `GetRecordedAudio` copy
   (251), slice (255-256), `committed=silence_start` + `silence_start=-1` stores (257-258), gain boost (259-263),
   and `CommitSegment` (264). `Finish`/`StopAndTranscribe` (376-490) and `TakeTail` (267-277) never acquire it —
   confirmed by grep (only two mentions of `commit_mutex_` in the .cpp: comment + lock). The pre-check at 221-223
   only returns early when `silence_start<0` at that instant; the full check is repeated under the lock, so it
   cannot skip a commit — sound TOCTOU-safe optimization.
2. **Lock ordering has no inversion I can construct.** Order is commit_mutex_ -> capture mutex ->
   StreamingDictator mutex_. (a) `CommitSegment` (StreamingDictation.cpp:74-84) takes only its own mutex_ briefly,
   notifies after release, never calls back into the engine — no streaming->commit edge. (b) Real capture:
   `AppendFrames` releases its mutex_ before `OnAudioChunk` (MiniaudioCapture.cpp:104-110), and `OnAudioChunk`
   never takes commit_mutex_ — no capture->commit edge. (c) Fake capture mirrors this (Fakes.h:58-63).
   (d) `Begin`/`Finish`/`Cancel`/`CommittedCount`/dtor take only StreamingDictator::mutex_; engine dtor joins the
   Run worker via `Stop()` before `streamer_` is destroyed (member order: streamer_ at DictationEngine.h:102 is
   destroyed after commit_mutex_ at :117, but no lock is held at destruction, so this is safe). No new deadlock
   surface: while holding commit_mutex_, a Tick waits at most for the capture mutex (held briefly by the audio
   thread, which never waits on commit_mutex_) and the streamer mutex (held briefly; the streamer worker does
   transcription outside the lock) — both make progress independently.
3. **The header comment overclaims.** DictationEngine.h:44-47 says "Tick is safe to call from more than one
   thread" with only the commit serialization as justification. But `Tick()` (DictationEngine.cpp:567-597) also
   does `HandleMicLost()` (device lost, 573-575), hands-free timeout -> `StopAndTranscribe` (581-586), max-recording
   timeout -> `StopAndTranscribe` (587-590), and ARMED timeout FSM trigger (592-595) — none of which is
   serialized. Two concurrent Ticks that both observe a timeout condition will both enter `StopAndTranscribe`,
   which does `capture_.Stop()`, `GetRecordedAudio`, `streamer_->Finish` (blocking CV wait + transcription),
   pipeline/inject, and FSM transitions concurrently. In *this test's* scenario that path is unreachable
   (FakeClock never advances, hands_free_ defaults false, now-capture_start=0 < 30000ms default), so the test is
   clean — but the public contract as written invites exactly the unsafe usage. This is the one MAJOR finding.
4. **Test structure is sound post-fix, empirical pre-fix.** The 8-thread go-flag barrier is an arrival barrier:
   threads increment `arrived` then spin on `go`; main waits for all 8 arrivals before setting `go`, so all
   threads are live and spinning when released. Post-fix the outcome is order-independent (the lock makes exactly
   one commit regardless of scheduling) — deterministic pass, confirmed 10/10 by reviewer. Pre-fix, failure
   requires all 8 threads to load identical `silence_start`/`committed` before the first store lands; that window
   is wide here (the ~64K-sample `GetRecordedAudio` copy + slice happen between load and store), making the
   reported 4/4 fail-before with exactly 8 duplicate commits highly credible on a multi-core box, but not
   *guaranteed* on a single-core/loaded runner — the implementer discloses this honestly (report §14).
5. **No Windows/GUI regression surface.** Diff touches only `src/core/DictationEngine.{h,cpp}` +
   `tests/test_streaming.cpp`; zero changes under `src/ui/` or `src/os/` [VERIFIED git diff --stat]. The
   typography/DPI bring-up fixes and Windows-only adapters are untouched.

## 4. Findings
### R-W3-002-001 [MAJOR] Header declares Tick multi-thread-safe; only the streaming commit is
- Location: `src/core/DictationEngine.h:44-47` · Evidence: `Tick()` at DictationEngine.cpp:567-597 calls
  `HandleMicLost()` (573), `StopAndTranscribe()` (584, 588), and FSM triggers (593) outside any serialization;
  `StopAndTranscribe` (376-490) performs capture stop, blocking `streamer_->Finish`, STT transcription, pipeline,
  injection, and FSM transitions. Two concurrent Ticks observing the same timeout/device-lost condition would both
  execute it — double transcribe/inject and FSM races, strictly worse than the bug ENG-B1 fixed. The implementer
  report §9 acknowledges non-commit Tick logic "remain[s] unsynchronized", directly contradicting the header.
- Why it matters: a future caller reading the public contract (the exact audience for this comment) can introduce a
  worse race believing Tick is safe. Production is single-worker today, so this is latent, not live — hence MAJOR,
  not BLOCKER.
- Recommended fix (root-cause level, docs-only, minimal): narrow the contract to what the fix provides, e.g.
  "The streaming-segment commit inside Tick is serialized by commit_mutex_ and is safe under concurrent Tick
  callers; the remainder of Tick (hands-free/max-recording timeouts, HandleMicLost) is still single-caller-only,
  as in production." Alternatively serialize all of Tick — rejected here as larger blast radius than ENG-B1's
  scope; the doc narrowing is the honest minimal fix. Also note `TakeTail()` (267) reads `committed_samples_`
  without commit_mutex_, so a concurrent commit racing StopAndTranscribe's tail slice is still possible under the
  current contract — pre-existing (see R-W3-002-002).

### R-W3-002-002 [MINOR] commit_mutex_ does not cover TakeTail/StopAndTranscribe tail read (pre-existing)
- Location: `src/core/DictationEngine.cpp:267-277`, called from `StopAndTranscribe` (404) ·
  Evidence: `TakeTail` loads `committed_samples_` unlocked; a concurrent `MaybeCommitStreamingSegment` could advance
  `committed` between StopAndTranscribe's `CommittedCount()>0` check and the tail slice, yielding a short/empty
  tail while the segment was also committed. Pre-existing (not introduced by this commit) and unreachable with the
  single production worker; inside ENG-B1's scope the commit itself is now correct. Recommend tracking as a
  known limitation (already partly disclosed in implementer §9) rather than fixing here.

### R-W3-002-003 [MINOR] "CommitSegment cannot throw" is inaccurate
- Location: implementer report §8 (not in code). `CommitSegment`'s deque `push_back` and the in-lock
  `GetRecordedAudio`/slice/`NormalizeLoudness` can throw `bad_alloc`. Harmless under `lock_guard` (lock released
  during unwind, no catch-and-continue), but the report's wording overstates. No code change needed; correct the
  record if the report is ever amended.

### R-W3-002-004 [NIT] Fail-before is empirical, not guaranteed, on single-core runners
- Location: `tests/test_streaming.cpp:236-256`. The barrier guarantees 8 threads are live, not that all 8 load
  before the first store; on a single-core/loaded CI the unfixed code could theoretically pass once, masking a
  regression. Post-fix the test cannot flake (order-independent). Implementer discloses this (§14); acceptable
  for a race regression test. Optional hardening (not recommended now): run the barrier loop a few times per case.
