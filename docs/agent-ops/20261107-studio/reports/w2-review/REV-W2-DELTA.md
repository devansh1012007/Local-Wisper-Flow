## 3. Findings

### D-MINOR-1 — Detach branch (LLM ignoring cancel >3 s) is untested and leaks a thread per hang; provider-lifetime hazard on shutdown

- **Where:** `DictationEngine.cpp:787-791` (`llm_worker.detach()` then restore + `LlmTimeout` return); captured raw `ILlmProvider* llm` (`:779-781`); `Stop()` joins only the engine worker (`:147-155`), never a detached LLM thread.
- **What:** with a cancel-responsive provider this branch is dead code — `LocalLlamaProvider` aborts per `llama_decode` step via `llama_set_abort_callback` (`LocalLlamaProvider.cpp:108-114`, flag reset at `:96`), `PassthroughLlm` returns instantly — so the worker-free claim holds for both prod providers. But the fix's stated purpose is an *uncooperative* LLM; that exact case has no test (the new `HungLlm` releases on `RequestCancel`, so it exercises the join path `:793`, never `:788`). If it ever fires: (a) each hung transform leaks one thread for the LLM's remaining lifetime, each subsequent transform/command/cleanup `Process` on the same provider serializes behind `LocalLlamaProvider::mutex_` (`LocalLlamaProvider.cpp:95`) — the engine worker is freed (good) but threads accumulate under repeated transforms; (b) `engine.Stop()` → stack teardown destroys `llama_provider` (`main.cpp:354`, destroyed after engine) while a detached thread may still be inside `Process` holding that pointer — a narrow UAF window at process exit (spurious crash report at worst). IMPR §5/§7 discloses both as accepted residuals; this review agrees the tradeoff beats re-wedging the worker (and beats `CommandModeController`, whose local `WorkerQueue` dtor join at `:97/14-22` actually blocks *forever* on a truly hung LLM), but it is not yet proven by test.
- **Fix direction (Wave 3, not this delta):** add an uncooperative-hang test (fake ignoring `RequestCancel`; assert restore + `LlmTimeout` + worker processes next event), and bound detached-thread lifetime (e.g. registry of detached tasks joined with timeout in `~DictationEngine`, or a shared ownership token for the provider). Do not "fix" by joining unconditionally — that reintroduces MAJOR-1.

### D-MINOR-2 — 8000 ms timeout is not configurable, and `transform_llm_timeout_ms_` is a plain `int` (future data race)

- **Where:** `DictationEngine.h:139` (`int transform_llm_timeout_ms_ = 8000`), setter `:273-275`, read `:784`; `SetTransformLlmTimeoutMs` is never called in `src/` (only the test) — no Settings key, no `main.cpp` wiring.
- **What:** (a) *Legit-run risk (probed, mitigated):* 512 max-predict tokens (`LocalLlamaProvider.h:14`) on a slow CPU can legitimately exceed 8 s, and the new timeout will now abort a run that previously (slowly) succeeded — a real behavioral change vs pre-delta. Mitigating facts: it exactly mirrors the pre-existing command-mode policy (`command_->Run(raw, 8000)` at `DictationEngine.cpp:598`), prompt size is bounded by the 2048-ctx guard (`LocalLlamaProvider.cpp:135`, which already throws for ~8000-char prompts), and transform outputs are edit-length, usually stopping at EOG long before 512 tokens. Net: consistent with house policy, not a regression — but unlike cleanup (`cleanup_timeout_ms`, 200-30000, GUI-exposed) there is no knob to raise it when Wave 4 ships the Transforms page.
- (b) *Race:* the setter is public and the read is on the worker thread; any post-`Start()` call (the obvious Wave-4 use) is a data race — the same defect class as the just-fixed `scratchpad_target_`. Today it is only called pre-run from tests, so no live UB.
- **Fix direction:** make it `std::atomic<int>` (one line, same pattern as `scratchpad_target_`), and expose a config key in Wave 4 alongside the transforms UI.

### D-MINOR-3 — Cap bounds the blowup but worst-case `Diff` at the cap is still ~370 MiB transient; capture copies the full selection before the cap

- **Where:** cap `:115,773-777` (engine-side, post-capture); `WindowsTextInjector.cpp:366-437` (capture copies `saved_clipboard_` + `selected` in full before returning); `TextDiff.cpp:89` (O(n·m) table).
- **What:** MAJOR-2's harms (uncaught OOM → worker `terminate`, clipboard unrestored) are closed: `Put` is now caught and runs after restore. The residual is transient cost, not correctness: 8000 chars of single-char tokens (4000 tokens) with a max-length result (24200 chars → 12100 tokens, allowed by the `3x+200` validator) allocates a (4001×12101)×8 B ≈ 370 MiB table (IMPR's "~100 MB" estimate understates the adversarial corner; realistic word-density input is ~60 MB). A smaller machine will `bad_alloc` — now safely swallowed, clipboard already restored, transform result already injected (diff is best-effort) — so this is a latency/jank risk, not a crash. Separately, the cap is enforced after `CaptureSelection` has already copied an arbitrarily large clipboard twice on the OS side (unbounded `std::string` alloc before rejection); copy-scale (linear) not quadratic, and the fake/OS seam is Wave-4 territory.
- **Fix direction (Wave 3, needs `TextDiff.*` which was correctly out of write-set):** fail-soft `Diff` above a token threshold (return `valid=false` instead of building the table) and/or move the size check into `CaptureSelection`. No change needed to accept this delta.

### D-MINOR-4 — Remaining unguarded throw sites in `HandleTransform` (thread spawn, prompt build, non-capture restores)

- **Where:** `std::make_shared<packaged_task>` + `std::thread` construction (`:780-783`, can throw `bad_alloc`/`system_error`), `BuildTransformPrompt` (`:778`), bare `RestoreClipboard()` calls (`:768,775,809-823,825`); `Run()`/`ProcessOne()` have no catch-all (`:157-182`).
- **What:** IMPR closed capture-throw and `Put`-throw; the remaining sites require resource exhaustion (thread/packaged_task/prompt alloc) or a throwing `RestoreClipboard` (Win-API wrapper, no-throw in practice) — all far less plausible than the closed branches, and `Run`'s lack of catch-all is pre-existing. But "restore on every branch" is still one `system_error` away from a worker `terminate` with the clipboard unrestored. Test suite covers the pinned branches well.
- **Fix direction:** wrap spawn+prompt in try/catch mapping to the generic failure (or hoist a `Run`-level catch-all that restores + reports). Small, Wave-3 welcome.

### D-MINOR-5 — Test-strength residuals from TREV P1s (partials, disclosed in part)

- **What:** none of these can produce a false green for the *fixes* in this delta (the new assertions themselves are behavioral and were run), but two TREV P1s are "fixed in the strengthened case, not everywhere."
